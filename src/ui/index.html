Install Android to a virtual disk

The VM window is open. Follow the 6 steps below once; afterwards ApkStart boots directly from the disk and no longer needs the image.

  1. Boot menu: use ↓ to select Installation - Install Android-x86 to harddisk, then press Enter
  2. Choose Partition: choose Create/Modify partitions; when asked whether to use GPT, choose No
  3. cfdisk partitions：New → Primary → press Enter for the size → Bootable → Write → type yes → Quit
  4. Format: choose vda1 → when prompted to format, choose ext4 → Yes
  5. Boot & system：Install GRUB select Yes；Install /system as read-write select Yes
  6. Done: when progress reaches 100%, click "I've finished installing" below (ApkStart will restart and take over automatically)

If adb reports not connected later: in the VM window press Ctrl+Alt+F1 enter the terminal and run setprop service.adb.tcp.port 5555、stop adbd、start adbd, then press Ctrl+Alt+F7 to return to the graphical interface.

Automatic mode (default, no setup needed)
Detecting…
Memory, cores, render backend, port and acceleration are all chosen automatically; failed launches retry with fallbacks, no manual changes needed. ApkStart uses Dedicated adb server port 5044 (your system adb uses 5037), so on the command line adb devices cannot see this Android device — this isolation is intentional. To connect, use $env:ANDROID_ADB_SERVER_PORT=5044 then run adb. Note: do not manually adb connect, which will pop up the "Allow USB debugging?" system dialog on top of the running app.

The system image is shared across the machine, while app data is stored in differential layers; old images, snapshots, logs and lock files can all be reclaimed. Logs roll over automatically when they exceed the limit. "Reset Android data" really deletes several GB of user data, keeping only the system itself.

App window
Press F11 or right-click the tray to switch; full screen only enlarges the window without changing the aspect ratio, and switching does not restart the app.
When on, every app opens full screen without pressing F11. Best combined with Landscape below: a landscape panel already matches the screen aspect ratio, so full screen leaves no black bars.
Android's orientation is determined by the real orientation of the virtual phone panel. When the panel orientation differs from what the app declares, Android shows the app in a narrow strip in the middle with black bars on both sides — resizing the window or changing resolution will not fill it. "Follow app" reads the app's orientation when the APK is installed and switches the panel to match at launch, so apps like Hongguo and Modu appear upright and full-screen. Only when the orientation is wrong does the runtime restart once (about ten seconds); afterwards apps with the same orientation open instantly.
Inside Android, the auto-rotate switch is on by default. Note this does not affect screen orientation: panel and screen orientation are still controlled by the strategy above + the "ignore app orientation requests" setting, and will not be skewed by sensors. Only a few apps read this switch.
At 190 dpi, 720 wide equals 606 dp, just past Android's 600 dp tablet breakpoint. The two-column episode page in Hongguo Short Drama and the split-pane settings page only appear at this layout. Turning it off returns to phone layout (larger text, less information). Takes effect the next time an app is opened.
This is the current physical panel orientation used by the runtime; it is written automatically by the strategy above. Only in "Force" mode is it fully up to you.
Native window is rendered and arranged directly by the emulator; dragging, resizing and rotating feel responsive with no black bars or click offsets, at the cost of an extra taskbar icon (use the tray menu or Ctrl+Alt+R in landscape). Embedded mode puts the emulator window inside ours: more unified and with a rotate button, but prone to frame drops and black bars when resizing, rotating or switching apps. Applies the next time an app opens.
In windowed mode you can drag the border to resize freely; this sets the internal Android render size. Smaller values use less performance.
Mouse buttons
The emulator natively treats left-click as a finger tap; press and drag to swipe. No extra configuration needed.
The emulator treats right-click as a tap by default (easy to trigger accidentally). When on, right-click only goes Back and no longer taps.
Smooth mode merges scroll ticks over a short interval into one swipe gesture, avoiding jerky stepping and spawning one adb process per tick.
Side-button mapping requires a global mouse hook. The hook is installed only while an ApkStart app window is in the foreground and is removed immediately when focus is lost or the window closes, so it never slows down the desktop.
These mappings work only while an app window is in the foreground; after switching to the desktop or closing the window, mouse behavior returns to native Windows.

Container details (advanced)
Limit vCPU quota and lower process priority so Windows desktop gets CPU first. The "Resource strategy" above already sets this automatically.
Game mode keeps the Android VM at a higher CPU priority and reduces host-side polling for the lowest input and display latency; other programs on the PC may slow down. When no app window is open, the container drops priority automatically.
Also disable background packages such as Play Store, Setup Wizard and Print Service, keeping only what apps need. If an app reports missing Google Play services, turning this off restores them.
After ApkStart starts, boot the Android environment in the background (the window stays hidden, so you never see the emulator). Every app launch then costs only one "open", measured at over 20 seconds down to almost nothing. The cost is about 1 GB of idle memory; with it off, the first app launch needs a cold boot.
The Android environment boots once and stays resident. Opening an app afterwards only starts that app and stops other app processes instead of rebooting the whole system. Closing the last window clears background apps and parks the container, and the next launch is still instant.
Download & update sources
"Auto" checks the latest release on both GitHub and Gitee, downloads 256 KB from each URL to measure speed, then downloads from the fastest one; one unavailable source does not block updates.
When direct GitHub is slow, also speed-test the public forwarding services ghfast.top / gh-proxy.com (they forward only public release files and never touch accounts). When off, only direct connections and your own prefix are used.
If set, only your prefix is used and the two public mirrors above are skipped; leave blank to let "Auto" decide. The downloader prepends it to the real URL.
Large files are downloaded in parallel chunks. The default 8 threads already saturate most home connections; try 16 on a stable network.
Gitee update source (optional)
This repository is public and Gitee's release list can be read anonymously, so the Gitee source works with this field left blank. Fill it only when Gitee rate-limits you (403/429) or you want to read private branches: gitee.com → Settings → Private token, check only "projects". It is used only to read release lists and never uploads anything.
System check · Auto configuration
First inspect this PC: is CPU virtualization on, is Windows Hypervisor Platform present, what GPU and VRAM, enough memory and OS version. Anything that can be changed automatically (memory / cores / quality / render backend) is written to settings and saved as a driver; items needing administrator rights get a button; BIOS-only items explain how to change them.
Drivers · compatibility patches
Some machines need extra boot parameters (old GPUs with low GLES versions, hardware acceleration disabled, a driver that crashes with hardware rendering). A driver is just a JSON file: "which machines to match" + "which boot parameters to change on match". You can write, import and share them. Drivers only change whitelisted boot options, Does not execute any code; it takes effect only when it matches.

Runtime
ApkStart runs only its own runtime: adb / emulator / system images are downloaded and managed by it. It does not detect, take over or depend on any emulator installed on your PC (MuMu / LDPlayer / BlueStacks / WSA are never used). Moving to another machine, whether an emulator is installed, or how it upgrades never affects ApkStart.
